# 🎙️ 브라우저단 AI 구현: 팀 설득을 위한 기술 증명 (PoC)

팀원들의 "서버(FastAPI)가 더 낫지 않아?"라는 의문을 해소하기 위해, 브라우저 단에서 모델이 어떻게 존재하고 작동하는지 기술적으로 증명합니다.

---

## 1. 모델은 '어디에' 있나요? (Hosting & Loading)

가장 많이 듣는 질문입니다. "모델 파일을 어디에 올리고, 브라우저가 그걸 어떻게 가져오지?"

- **저장소 (Storage)**: 모델(ONNX 파일)은 이미지나 CSS 파일처럼 **프론트엔드 정적 서버(Nginx, S3 등)**에 올려둡니다.
- **배달 (Delivery)**: 유저가 겜에 접속할 때, 브라우저가 이 파일을 쓱~ 다운로드합니다. (한 번 받으면 브라우저 캐시에 저장되어 다음부턴 1초도 안 걸립니다.)
- **실행 (Operation)**: `transformers.js` 라이브러리가 유저의 **컴퓨터 메모리(RAM)**에 모델을 올리고, 유저의 **CPU/GPU**를 빌려 연산합니다.

> [!TIP]
> **팀원 설득 포인트**: "우리는 GPU 서버 한 달에 수십만 원 낼 예산이 없지만, 유저들의 컴퓨터 성능을 빌려 쓰면 **서버 비용이 0원**입니다!"

---

## 2. 전체 데이터 전파 과정 (Full Loop Proof)

브라우저 단 AI가 어떻게 다른 유저의 화면까지 영향을 주는지 증명하는 6단계 흐름입니다.

1.  **[감지]** 유저의 마이크 입력을 **Web Speech API**가 가로채서 텍스트로 변환.
2.  **[연산]** 브라우저 속 **ONNX 모델**이 실시간으로 "95% 확률로 욕설!"이라고 판정.
3.  **[보고]** 프론트엔드가 이미 연결된 **게임 서버(Spring WebSocket)**에 쏘아 올림.
    - `send("{ type: 'TOXIC', text: 'XXXX' }")`
4.  **[검증]** 백엔드(Spring)는 이 메시지를 받고, "오 마침 user1이 욕을 했군! 독 버프를 걸어라!"라고 **서버 틱(Tick)**에 반영.
5.  **[전파]** 백엔드가 4명의 유저 모두에게 **WebSocket**으로 뿌림.
    - `broadcast("{ type: 'STATUS_CHANGE', user: 'user1', status: 'POISONED' }")`
6.  **[출력]** 각 유저의 **React/Phaser**가 이 메시지를 받자마자 user1의 머리 위에 해골을 띄우고 조작을 반전시킴.

## 3. "보안은요?"에 대한 대답

**팀원 우려**: "유저가 프론트엔드 코드를 조작해서 욕설 감지를 무력화하면 어떡해?"

**우리의 반론**: 
1.  **게임의 성격**: 이 게임은 랭킹 경쟁 게임이 아니라 친구들끼리 즐기는 '심리 협동 게임'입니다. 해킹해서 욕을 마음껏 하는 건 게임의 재미를 스스로 망치는 행위일 뿐입니다.
2.  **이중 검증**: 정 불안하다면, 욕설이 감지되었을 때 **텍스트만 따로 백엔드에 보내서** 백엔드가 아주 가벼운 키워드 필터링만 거치게 할 수도 있습니다. 굳이 무거운 AI 서버(FastAPI)를 24시간 돌릴 필요가 없습니다.

## 4. 맛보기 실습 (How to start)

팀원들에게 **"자, 여기 봐봐. 서버 없이도 돌아가지?"**라고 보여줄 수 있는 순서입니다.

1.  HuggingFace의 Unsmile 모델을 **ONNX**로 변환한다.
2.  `transformers.js` 라이브러리를 React에 설치한다.
3.  버튼을 누르면 마이크가 켜지고, 내가 하는 욕을 브라우저가 알아듣는 걸 보여준다.

## 5. SFU(LiveKit) vs AI 서버: 누가 더 힘들까요?

사용자님이 말씀하신 **"SFU(영상 배달)가 사람이 많아지면 더 힘든 거 아냐?"**라는 의문은 매우 날카로운 지적입니다. 하지만 '하는 일의 성격'을 보면 답이 나옵니다.

### 🐦 일의 강도 비교 (비유)
- **SFU (LiveKit)**: **'택배 분류원'**. 들어온 택배(영상 패킷)를 뜯지 않고 주소만 보고 다른 유저에게 복사해서 보내주기만 합니다. (단순 노동 = 빠름)
- **AI 서버 (FastAPI)**: **'번역가/분석가'**. 들어온 택배(음성/텍스트)를 일일이 다 뜯어서 내용을 읽고, "이게 과연 욕일까?"라고 깊이 고민(연산)해야 합니다. (지적 노동 = 느리고 비쌈)

### 📈 인원 증가 시 시나리오 (100명 접속 시)
1.  **브라우저 AI 방식 (우리의 선택)**:
    - **SFU 서버**: 100명의 영상을 배달하느라 바쁘지만, '생각'은 안 합니다. (단순 배달)
    - **AI 연산**: 100명의 유저 컴퓨터가 각자 자기 것만 연산합니다. **서버의 머리(CPU/GPU)는 하나도 안 씁니다.**
2.  **FastAPI 방식 (팀원 제안)**:
    - **SFU 서버**: 영상 배달하느라 이미 바쁩니다.
    - **AI 서버**: 100명의 음성을 실시간으로 다 분석해야 합니다. **슈퍼컴퓨터급 GPU 서버가 여러 대 필요하고 비용이 폭발합니다.**

### 🏆 결론
SFU(LiveKit)는 영상 채팅을 위해 **어차피 운영해야 하는** 필수 시설입니다. 여기에 무거운 **AI 분석 업무**까지 서버에 얹는 것은 "배달원에게 번역 업무까지 시키는 것"과 같습니다. 

따라서 **분석(AI)은 각 유저의 브라우저**에게 맡기고, **배달(LiveKit)**만 서버가 담당하는 것이 서버 수명을 늘리고 비용을 아끼는 가장 똑똑한 설계입니다!

## 6. 자원 사용량 분석: 램(RAM)은 얼마나 먹을까요?

사용자님이 걱정하시는 **"4GB(권장 1.5GB) 안에서 해결 가능할까?"**에 대한 답변입니다. 결론부터 말씀드리면, **"양자화(Quantization)" 기술을 쓰면 충분히 가능**합니다.

### 🐦 Unsmile 모델 RAM 예측도
| 구분 | 원본 모델 (fp32) | 양자화 모델 (int8) | 비고 |
| :--- | :--- | :--- | :--- |
| **모델 파일 크기** | 약 440MB | **약 110MB** | 다운로드 용량 |
| **예상 RAM 점유** | 약 800MB ~ 1GB | **약 200MB ~ 300MB** | 실행 시 메모리 |

### 🍱 전체 시스템 메모리 시뮬레이션
*   **브라우저 기본 + OS**: 약 500MB
*   **게임 (Phaser 3 + Assets)**: 약 300MB ~ 500MB
*   **AI 모델 (int8)**: **약 300MB**
*   **기타 (WebRTC, WebSocket)**: 약 100MB
*   ---
*   **합계**: **약 1.2GB ~ 1.4GB** 🏆 (1.5GB 목표 달성 가능!)

### 💡 팀원 설득용 필살기: "양자화(Quantization)"
"모델을 그냥 올리는 게 아니라, **8비트(int8)로 압축(양자화)**해서 올릴 거야. 성능은 거의 비슷하면서 크기와 램 사용량은 **1/4로 줄어드니까**, 게임이랑 같이 돌려도 1.5GB 안에서 충분히 쾌적하게 돌아가!"라고 말씀해 보세요.
