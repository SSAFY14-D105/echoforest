# 🎙️ STT 엔진 선정 (Decision Record) — 런타임은 왜 Web Speech API인가

게임 음성채팅에서 **욕설을 탐지**하려면 먼저 음성을 텍스트로 바꿔야 한다(STT). 이 폴더는 **실시간 게임 런타임에서 쓸 STT 엔진**을 고른 *결정 기록*이다. (정확도 벤치마크가 아니라 **아키텍처 결정**임에 유의)

> **결론**
> - **런타임(브라우저) STT = Web Speech API** ✅ — 실시간·무인프라·한국어 욕설 인식 충분.
> - **오프라인 학습데이터 수집 STT = faster-whisper large-v3** (`../../0_Data_Collection/02_stt`) — 정확도 최우선.
>
> STT를 **두 작업으로 분리**했다. "실시간으로 텍스트만 빨리 뽑는" 런타임과 "느려도 정확해야 하는" 데이터 라벨링은 요구사항이 정반대라, 한 엔진으로 둘 다 하지 않는다.

## 📒 증거 원장 — 무엇을 측정/논증했고, 무엇을 못 했나

이 결정의 근거를 정직하게 라벨링한다(과장 금지).

| 구분 | 내용 | 근거 |
| :--- | :--- | :--- |
| ✅ **측정함** | 응답지연 **~669ms**(발화→첫 인식), 한국어 인식 confidence 84~87% | [`web_speech_api/test_web_speech.html`](web_speech_api/test_web_speech.html) (재현 가능) |
| ✅ **정성 확인** | 한국어 구어체 + **욕설을 검열 없이 원문 인식** | [`web_speech_api/webspeech_sample_*.txt`](web_speech_api/) |
| 🧩 **논증(설계)** | 무인프라·실시간·배포 단순 → 런타임 적합 | 아래 §1–§3 |
| ⚠️ **못 잼(리스크)** | STT **정확도/WER** — 정답(ground-truth) 전사가 없어 수치화 불가 | — |
| ⚠️ **못 잼(리스크)** | **train(whisper)/serve(web-speech) 분포 skew** | §4 (측정 절차 제시) |

> 즉 "Web Speech가 정확하다"를 숫자로 증명한 게 아니라, **런타임 요구(실시간·무인프라·욕설 인식)에 충분하고 실용적**이라는 *엔지니어링 결정*이다. 정확도 리스크는 §4처럼 **인지하고 관리**한다.

## 1. 런타임 STT의 요구사항

게임 안 STT는 그 자체가 목적이 아니라 **욕설탐지 모델의 입력(텍스트)** 을 만드는 수단이다.

| 요구 | 이유 |
| :--- | :--- |
| **저지연** | 발화 → 저주 스택 반영이 즉각적이어야 게임이 됨(60FPS 프레임 유지) |
| **무인프라·저비용** | 4인 멀티플레이 웹게임. 세션마다 GPU STT 서버는 배포·비용상 비현실적 |
| **한국어 + 욕설 인식** | 입력이 욕설이므로 비속어를 **검열 없이 원문 그대로** 받아야 함 |
| **튜닝 깊이** | ❌ 불필요 — 텍스트만 나오면 됨. AI 역량은 *분류 모델*에서 증명 |

핵심: 이 프로젝트의 AI 난이도·기여는 STT가 아니라 **"그 텍스트를 욕설/clean으로 분류하는 모델(UnSmile fine-tuning)"** 에 있다. STT는 잘 만들어진 걸 실용적으로 쓴다.

## 2. 후보 3안 비교

| 항목 | Web Speech API (브라우저) | 로컬 Whisper (Transformers.js) | faster-whisper 서버 (FastAPI+CUDA) |
| :--- | :--- | :--- | :--- |
| 처리 위치 | ☁️ 브라우저→구글 | 🖥️ 브라우저 On-Device | 🚀 로컬 GPU 서버 |
| 지연 | ⚡ 실시간(측정 ~669ms) | 🐢 3~5초+ (WASM) | ⚡ 0.2~0.5초 |
| 한국어/욕설 | ✅ 충분(욕설 원문 인식) | ⚠️ 낮음(tiny 한계) | ✅ 최상(large-v3) |
| 인프라/비용 | ✅ **없음** | ✅ 없음(대신 CPU 폭증) | ❌ 세션마다 GPU 필요 |
| 배포 난이도 | ✅ 코드 몇 줄 | ⚠️ 번들·성능 | ❌ 서버 운영 복잡 |
| 튜닝(VAD·빔서치) | ❌ 블랙박스 | ⚠️ 제한 | ✅ 자유 |

- **로컬 Whisper(WASM)**: 브라우저 CPU로 3~5초씩 밀려 실시간 게임 부적합 → 탈락.
- **faster-whisper 서버**: 빠르고 정확하지만 **웹 멀티플레이에서 클라이언트별 GPU 추론 서버는 비현실적**(비용·확장성) → 런타임엔 과함.
- **Web Speech API**: 인프라 0, 실시간, 한국어·욕설 인식 충분 → **런타임 채택**.

## 3. Web Speech API의 trade-off — 알고도 받아들인 이유

| 단점 | 받아들인 근거 |
| :--- | :--- |
| **블랙박스**(VAD·빔서치 튜닝 불가) | 런타임 STT엔 그 튜닝이 불필요. 텍스트만 확보하면 됨 |
| **크롬 의존**(`webkitSpeechRecognition`) | 타깃이 데스크톱 크롬 웹게임이라 허용 범위 |
| **클라우드 전송**(구글) | 음성은 즉시 텍스트화되어 게임 로직으로만 흐름. 저장하지 않음 |
| **인식 흔들림**(run-on·오탐) | 뒤단 분류 모델을 **게임 STT로 fine-tuning**해 흡수(단, §4 skew 주의) |

## 4. ⚠️ train/serve 정합성 — 알려진 리스크 (가장 중요)

이 결정의 **가장 큰 미해결 리스크**다. 학습과 런타임이 **다른 STT 엔진**을 쓴다:

- **학습데이터**: faster-whisper 전사 → 에러 스타일 = **환각**(외국어 gibberish, 예 "무레호 유노쿠…"), 비교적 문장형
- **런타임 입력**: Web Speech 전사 → 에러 스타일 = **음차 오류**(남진/수봉/봉다리), run-on

분류기는 whisper 스타일로 학습되는데 런타임엔 web-speech 스타일이 들어온다 → **스타일 갭이 존재**(정성 확인). 크기는 **아직 미측정**.

**닫는 법(측정 절차)**
1. 같은 음성을 두 엔진으로 전사 → **CER/WER**와 **분류 결과 일치율** 비교.
   - Web Speech는 마이크 입력 전용이라 페어 전사엔 **수동 캡처** 필요: 오디오를 `test_web_speech.html`에 흘려보내 전사 → whisper(`02_stt`)와 대조.
2. 완화책: ① web-speech 전사도 학습/평가셋에 **섞기** ② 최소한 web-speech 전사체로 모델 **평가 1회**.

> ※ `webspeech_sample_*.txt`는 이 비교에 **그대로 못 쓴다** — 파이프라인 audio_1(피코파크)과 **다른 영상**(좀비 서바이벌)이고 정답 전사도 없다. §아래 참고.

## 5. faster-whisper는 버린 게 아니다 — 데이터 수집으로 재배치

| 작업 | 엔진 | 우선순위 |
| :--- | :--- | :--- |
| **런타임**(게임 중 실시간) | Web Speech API | 속도·무인프라 |
| **데이터 수집**(오프라인 라벨링) | faster-whisper large-v3 | 정확도 |

라벨링용 코퍼스는 느려도 **정확도가 생명**이라 GPU Whisper가 맞다([`../../0_Data_Collection/02_stt`](../../0_Data_Collection/02_stt)).
