# 📄 질문서: 음성 인식 기반 게임 내 제재 시스템 구축을 위한 모델 파인튜닝 및 전처리 전략 상담

## 1. 프로젝트 개요
- **주제**: 4인 협력 멀티플레이 게임(마리오 스타일) 내 음성 채팅 분석 및 페널티 시스템
- **목표**: 플레이어의 음성을 실시간으로 분석하여 **욕설**뿐만 아니라 팀 사기를 떨어뜨리는 **부정적인 언어(짜증, 남 탓, 비꼬기 등)**를 탐지해 게임 내 페널티(저주)를 부여함.
- **파이프라인**:
  1. Frontend: Web Speech API로 음성 수집
  2. Server: STT(Speech-to-Text)로 텍스트 변환
  3. AI: `Unsmile` 모델(한국어 혐오 표현 탐지)을 파인튜닝하여 멀티 라벨 분류
  4. Game Logic: 감지된 라벨에 따라 실시간 페널티 적용

---

## 2. 현재 상황 및 문제점

### (1) 데이터 수집 및 전처리 (Audio Chunking)
- **상황**: Unsmile 모델을 파인튜닝하기 위해, 실제 게임 환경과 유사한 **'유튜버들의 협력 게임 영상'**을 수집하여 학습 데이터로 만들고 있습니다. Python의 `pydub.silence` 모듈을 사용해 음성을 문장 단위로 자르고 있습니다.
- **문제점 (지연 시간/Chunking)**:
  - 유튜브 영상(학습 데이터)은 여러 명이 동시에 빠르게 말하거나 대화가 겹치는 상황이 많습니다.
  - `min_silence_len`(묵음 기준)을 **100ms**로 주면 "아...", "그..." 같이 의미 없는 단어 단위로 너무 잘게 쪼개져 문맥이 파괴됩니다.
  - **200ms 이상**으로 주면, 말이 빠른 구간에서 문장이 너무 길게 이어져(Chunking이 안 됨) 실시간 분석 단위로 적절하지 않습니다.
  - **괴리감**: 실제 우리 게임 환경(User)은 각자 집에서 말하므로 입력이 비교적 또렷하고 끊겨서 들어오는데, 학습 데이터(유튜브)는 오디오가 겹치고 연속적이라 **데이터의 도메인 차이(Distribution Shift)**가 우려됩니다.

### (2) 데이터 정제 (STT vs 텍스트 데이터 괴리)
- **상황**: Unsmile 데이터셋은 인터넷 댓글 기반이라 자음(ㅋㅋ, ㅎㅎ, ㅇㅇ)이 많습니다. 반면, STT 결과물은 자음만 출력되는 경우가 거의 없고 억지로 단어로 변환하거나 생략해버립니다.
- **고민**:
  - 자음을 다 지우자니 "안해(부정)" vs "안해ㅋㅋ(장난)" 같은 뉘앙스 차이가 사라져 데이터의 질이 떨어질 것 같습니다.
  - 그대로 두자니 실제 STT 환경에서는 들어오지 않을 데이터라 학습 효율이 떨어질 것 같습니다.

## 3. 핵심 질문 사항

### Q1. 연속적인 대화 데이터(유튜브)를 학습 데이터로 구축할 때의 최적의 전처리(Segmentation) 전략은 무엇인가요?
현재 단순 `Silence` 기반(100ms~200ms)으로 자르고 있는데, 유튜브 영상처럼 대화가 끊이지 않는 소스를 **의미 있는 문장 단위**로 자르기 위해 현업에서는 어떤 기법을 주로 쓰는지 궁금합니다.
- 단순히 묵음 길이를 조절하는 것 외에, **VAD(Voice Activity Detection)**나 에너지 기반의 다른 분할 방식을 도입해야 할까요?
- 혹은 200ms로 길게 잘리더라도, 학습 시에는 문제가 없을까요? (실제 인퍼런스 때는 짧게 들어올 예정입니다.)
- **"문장이 끝났다"**고 판단하는 기준을 STT 텍스트의 완성도(문법적 종결 어미 등)를 보고 후처리를 하는 게 나을까요?

### Q2. 텍스트 데이터(Unsmile)와 STT 결과물 간의 불일치(Mismatch) 해결 방안
기존 Unsmile 데이터셋(텍스트 기반, 자음/이모티콘 포함)과 저희가 사용할 STT 데이터(음성 기반, 자음 생략됨)의 성격이 다릅니다. 이럴 경우 파인튜닝 데이터셋 구성을 어떻게 하는 것이 유리할까요?
1. **Unsmile 데이터를 STT처럼 변환**: 기존 데이터셋에서 자음(ㅋㅋ, ㅎㅎ)을 모두 제거하거나 정제하여 STT 출력과 유사하게 만든 뒤 학습시킨다.
2. **STT 데이터를 텍스트처럼 보정**: STT 결과물에 후처리를 하거나, 모델이 자음 없이도 문맥을 이해하도록 놔둔다.
3. **자음 삭제 시 의미 왜곡 문제**: "ㅋㅋ"를 지웠을 때 문장이 너무 딱딱하게(부정적으로) 해석되는 문제를 방지하기 위한 노하우가 있을까요?

### Q3. '팀 사기 저하(Negative Morale)' 라벨 추가 및 파인튜닝 전략
기존 Unsmile의 라벨(욕설, 혐오 등)에 더해 **"짜증/팀 사기 저하"**라는 새로운 클래스를 추가하여 **Multi-label Classification**을 하려고 합니다.
- 기존 Unsmile 모델의 가중치를 유지하면서 새로운 클래스만 잘 학습시키기 위해 추천하는 파인튜닝 전략(예: 일부 레이어 Freeze 등)이 있을까요?
- 유튜브 데이터 라벨링 시, 명확한 욕설이 아닌 "아 진짜 왜 저래(짜증)" 같은 애매한 감정 데이터를 일관성 있게 라벨링 하기 위한 팁이 있을까요?

### Q4. 실시간성 확보를 위한 모델 서빙 조언 (추가 질문)
게임 플레이 중 딜레이 없이 페널티를 주려면 추론 속도가 중요합니다. BERT 기반인 Unsmile 모델이 실시간 게임(초당 프레임이 중요한 환경) 서버에서 돌기에 무겁지 않을지 우려됩니다.
- 경량화(Distillation)를 고려해야 할까요, 아니면 비동기 처리로 결과만 늦게(1~2초 뒤) 줘도 사용자 경험에 큰 해가 없다고 보시나요?

---

### [참고: 작성 팁]
*   **Q1의 배경**: 질문자님이 고민하신 `100ms` vs `200ms` 딜레마는 **VAD(Voice Activity Detection)**라는 기술적 키워드와 연결됩니다. 이를 언급하면 "아, 이 학생이 뭘 고민하는지 정확히 아는구나"라고 생각하실 거예요.
*   **Q2의 배경**: 이를 **Data Mismatch** 또는 **Domain Shift** 문제라고 합니다. 텍스트 모델(BERT 등)은 문어체에 강하고 STT는 구어체라 이 간극을 줄이는 게 핵심입니다.
*   **Q3의 배경**: 기존 모델에 라벨을 추가하는 것을 **Transfer Learning(전이 학습)에서의 Head 교체/추가**라고 합니다.
