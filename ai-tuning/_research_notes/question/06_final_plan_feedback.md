# 🕵️‍♂️ 최종 계획 점검 및 피드백 보고서

현재 작성된 `04_final_decision_summary.md`는 매우 체계적이고 현실적인 전략을 담고 있어 **성공 확률이 높은 (95점)** 계획입니다. 하지만 "완벽"을 위해 개발 단계에서 마주칠 수 있는 사소한 구멍(Pitfalls)들을 미리 메우기 위한 피드백을 드립니다.

---

## 1. 데이터 불균형 전략의 과잉 보정 (Over-correction) 주의
**현재 계획**: `Oversampling(5배)` + `Weighted Random Sampler` + `Weighted Loss` (3중 적용)
- **피드백**: 이 3가지를 동시에 적용하면 모델이 새로운 라벨(`positive_morale`)에만 과도하게 집중하여, 오히려 기존의 욕설/혐오 탐지 능력이 망가질 수 있습니다.
- **수정 제안**: **2가지만 선택**하는 것이 안전합니다.
    - **Recommended**: `Oversampling(3~5배)` + `Weighted Loss` 조합.
    - `Weighted Random Sampler`는 구현이 까다롭고 배치 단위 통제가 어려울 수 있어, 단순 오버샘플링이 직관적입니다.

## 2. VAD 라이브러리의 윈도우 호환성 및 오디오 규격
**현재 계획**: `webrtcvad` 사용
- **피드백**:
    1. **설치 이슈**: `webrtcvad`는 C++ 기반이라 윈도우(Windows) 환경에서 설치 시 `Microsoft C++ Build Tools` 에러가 자주 발생합니다. 에러 발생 시 `silero-vad`(PyTorch 기반)로 우회하거나 Docker 환경을 고려해야 합니다.
    2. **오디오 규격 강제**: `webrtcvad`는 반드시 **16kHz, 16bit, Mono PCM** 데이터만 받습니다. `pydub` 등으로 변환하는 전처리 코드가 필수입니다.
- **수정 제안**: `audio_transcriber_web.py` 작성 시, VAD 입력 전 `audio.set_frame_rate(16000).set_channels(1)` 변환 로직을 반드시 포함하세요.

## 3. Web Worker와 렉(Lag)의 진짜 원인
**현재 계획**: STT 결과 처리 로직을 Web Worker로 분리하여 40% 성능 향상 기대
- **피드백**:
    - 만약 **AI 추론(Inference)**이 서버에서 이루어진다면, 클라이언트(브라우저)가 하는 일은 단순히 텍스트를 `socket.emit` 하는 것뿐입니다. 이 정도는 메인 스레드에 거의 부하를 주지 않습니다.
    - **진짜 렉의 원인**은 십중팔구 **LiveKit 비디오 디코딩**이나 **Canvas 렌더링**입니다.
- **수정 제안**:
    - STT Worker 도입은 찬성하지만, 렉이 여전하다면 **"STT 때문이 아니다"**라고 빠르게 판단하고 LiveKit 해상도를 낮추거나 게임 프레임 제한(30fps)을 거는 쪽으로 선회해야 합니다. 잘못하면 효과 없는 최적화에 시간을 쓸 수 있습니다.

## 4. 자음 복원 규칙의 부작용 (Side Effect)
**현재 계획**: `ㅋㅋ` → `하하` 또는 `비꼼`
- **피드백**: 규칙 기반으로 `ㅋㅋ`를 무조건 `비꼼`으로 바꾸면, 정말 즐거워서 웃는 상황도 부정적으로 학습될 위험이 큽니다.
- **수정 제안**:
    - 확실치 않으면 **중립적인 단어**(`[웃음]`)로 바꾸거나, 긍정/부정 판단이 어려운 짧은 `ㅋㅋ`만 있는 문장은 **학습 데이터에서 제외**하는 것이 품질 관리에 더 유리합니다. "잘못된 데이터 1개가 잘된 데이터 10개를 망칩니다."
